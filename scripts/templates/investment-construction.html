07 / Portfolio construction

Optimized weights, judged out of sample.

Beyond fixed allocations, Strata solves for weights at each rebalance using a trailing return window. The resulting weights earn only subsequent returns. Twelve registered methodologies include minimum variance, risk parity, maximum diversification and maximum Sharpe, with both the original implementations and newer convex formulations available for comparison.

The convex layer uses cvxpy to solve supported objectives and mandates, reporting solver status and constraint dual values. A valid convex formulation can establish a global solution within numerical tolerances; that is not a guarantee of future investment performance. Unsupported combinations, numerical failures and infeasible mandates must be distinguished from successful solutions.

Risk estimates can use sample covariance, Ledoit-Wolf shrinkage or a statistical factor model. The factor count follows the Marchenko-Pastur noise edge rather than a manually tuned count. Its factor representation reduces the size of the risk calculation for larger universes.

Supported mandates include position caps, sector and country limits, turnover budgets and tracking-error ceilings. Cost-aware methods can include spread and convex market-impact terms. Which constraints a method supports is part of its contract, not a promise that every combination works with every objective.

This reproducible comparison uses the original registered minimum_variance and risk_parity methods, not their separately registered convex variants. Equal weight resets to 12.5% per security; XIC is held without rebalancing. The initial calibration period is excluded for every rule.

Minimum variance lost to equal weighting on Sharpe. In this selected sample, minimum variance earned a 0.79 Sharpe ratio versus 1.00 for equal weighting, with about 2.7 times its turnover. It did achieve lower realized volatility, consistent with its objective. A mathematically optimal allocation under estimated inputs is not necessarily the best realized investment.

This is consistent with the estimation-error concern studied by DeMiguel, Garlappi and Uppal (2009), not a replication of their study or proof that estimation error alone caused this result. Objectives, constraints, costs and the selected sample also matter. The system surfaces the comparison rather than assuming a more sophisticated method must win.

08 / Research to production

A contract between a researcher's rule and running software.

A construction rule starts as a description of what to solve. Turning it into dependable software means defining the inputs it may see, the weights it must return and the checks that detect a broken change.

Each methodology is a function from a context to a weight vector, registered with metadata. The API advertises that registry, the interface builds its menu from it and the walk-forward loop uses the same contract. New methods therefore reuse the existing execution and validation workflow.

The conformance gate applies fifteen checks to every registered method: valid weights, respected constraints, repeatable results, asset-order invariance, degenerate inputs and a solve-time budget. It runs in GitHub Actions and fails the build when a required check fails. Tests deliberately supply broken methodologies to verify that the gate rejects them. All twelve registered methods currently pass.

What the gate caught: the documented initial maximum-Sharpe implementation exceeded its 750 ms solve-time budget by using redundant restarts on convex subproblems. Later checks caught mandate parameters leaking between objectives and a ratio transform whose answer changed when returns were expressed in different units. These are software defects with investment consequences, not just presentation issues.

Every result carries a run identifier based on the request, price data and source code, with library versions recorded alongside it. These records help reviewers establish whether they used the same inputs and implementation. Saved study links are convenient starting points; the run record is the evidence to compare before treating two results as identical.

The deployed application reports progress, caches matching results and reports data-source failures without silently substituting frozen prices. Yahoo throttling, cold starts and the unauthenticated public endpoint remain operational limitations.
