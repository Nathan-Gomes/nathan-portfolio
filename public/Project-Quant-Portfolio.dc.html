Research question

How should a quant research idea become a repeatable process?

The experiment tests a six-ETF portfolio covering Canadian equities, US equities, developed international equities, emerging markets, aggregate bonds, and gold.

The strategy maximizes expected Sharpe ratio subject to long-only weights, full investment, and a 30% cap per asset. It is compared with SPY using only information available before each rebalance date, with transaction costs charged whenever weights change.

The larger focus is engineering discipline: separate configuration, SQL storage, pandas analytics, MATLAB verification, tested calculations, and documented assumptions.

Research-to-production workflow

A configuration change reruns the complete experiment and regenerates every output.

01

SQL data layer

Freeze adjusted prices, validate ticker/date records, and query market history from SQLite.

02

Python risk engine

Use pandas and NumPy to calculate returns, covariance, volatility, drawdown, Sharpe, and VaR.

03

Optimization model

Solve minimum-variance and maximum-Sharpe allocations with long-only and max-weight constraints.

04

Model support

Cross-check optimization in MATLAB, run pytest checks, and publish documented research outputs.

Role alignment

Built like a small quant research support tool

SPY produced the higher raw return in this sample. The optimized portfolio produced lower volatility, a smaller maximum drawdown, and a higher Sharpe ratio after modeled transaction costs. The report presents that trade-off directly instead of claiming an unrealistic win.

That structure mirrors quant developer work: interpret the financial question, implement the analytics, test the calculations, document the assumptions, and make the research reproducible.

Engineering controls

  • Python and pandas return/risk pipeline
  • SQL CTEs, joins, aggregations, and window functions
  • MATLAB quadprog comparison for the minimum-variance model
  • Pytest coverage for returns, weights, constraints, drawdowns, and chronology
  • No look-ahead in the rebalance loop
  • Configuration-driven assumptions for lookback, rebalance frequency, weight caps, costs, and benchmark
