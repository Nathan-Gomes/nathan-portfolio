ReliabilityML

An incident intelligence platform on simulated telemetry. It decides when something is wrong, names the likely cause or admits it doesn't know, tracks error budgets, answers troubleshooting questions only from approved runbooks, and gates releases and model promotions on measured evidence.

The project question: can a small platform shorten the path from a raw alert to a decision an engineer can trust, and show honestly where machine learning beats a well-written rulebook and where it doesn't?

01

The problem

Alert fatigue, slow root-cause analysis, and runbooks nobody can find.

On-call engineers lose time in three places: alerts that fire on harmless blips, the first minutes spent working out what kind of failure this is, and hunting for the runbook section that says what to do. A confident wrong answer in any of the three is worse than none, so every automated step here has to show its evidence and know when to stay quiet.

Foundation

Telemetry hard enough to mean something

Five services emit latency, errors, load, logs and traces every 15 seconds. Faults propagate through the call graph, so database saturation raises upstream errors and a traffic spike looks like saturation. 88% of deploys are harmless, and short noise spikes are not incidents.

02

Detection

Alerting faster usually means more false alarms. The curve makes the trade-off explicit.

Each signal gets a robust EWMA baseline built only from earlier minutes. A first version missed large error spikes because the incident inflated its own baseline; clipping each value before it updates the baseline fixed that. The operating point was chosen on the training days, then scored once on the test week.

The weak spot, stated plainly: memory leaks climb slowly enough that an adapting baseline treats them as normal. They are caught only when containers start restarting, hours in. A trend detector on memory is the next improvement.

03

Classification

The model beats the rulebook, and says "unknown" for the failure it never saw.

A random forest trained on four failure types, compared with if/then rules written from the runbooks. The rules even include a memory-leak rule the model never had. Confidence alone was not enough to catch the unseen type: the forest labelled most leak windows as traffic spikes with high confidence. A novelty guard, which measures distance to the nearest training examples, fixed it.

  • Every run is tracked in MLflow with parameters, metrics, the confusion matrix, feature importance, the model file, the git commit and the dataset version.
  • Promotion uses registry aliases (staging and production). The API serves whichever version holds production.
  • Features at time t use only data up to t, and a test rewrites the future to prove it.
04

SLOs and error budgets

Page on fast budget burn, not on every blip.

99.9% availability and 99% of requests under 300 ms, each over 30 days. Alerts use the multi-window burn-rate rules from the Google SRE Workbook: a page fires only when both the long and the short window burn faster than the threshold. The budget also drives release policy: below 25% remaining, only urgent fixes ship.

05

Troubleshooting assistant

Cited answers from approved runbooks, or a plain refusal.

Seventeen synthetic runbooks, postmortems and policies are split by section. Every sentence of an answer cites the section it came from, and code rejects any answer that cites something it did not retrieve. When the evidence is weak it replies "I couldn't find this in the approved runbooks or postmortems."

06

Drift and deployment

Retrain when the data moves, and promote only on evidence.

A simulated platform upgrade shifted latency by 20% and changed the request mix. Drift detection flagged it immediately (PSI 7.9), the pipeline retrained, and the candidate tied the production model, so it was not promoted. The reason is measurable: the model's inputs are relative to each window's own baseline, and they barely moved.

07

Limitations and next steps

What synthetic data can and cannot show.

The same person wrote the simulator and the models, so the scores are optimistic, and 19 test incidents make each per-class number fragile. The results demonstrate the method, not real-world accuracy.

Known gaps

Where it falls short today

  • Memory leaks are detected late, at container restarts.
  • The key-less assistant quotes sentences but cannot synthesize; 4 of 25 answers were relevant but incomplete.
  • The GCP deployment is defined in Terraform and validated in CI but has not been applied.

With real telemetry

What would change

  • Labels from real postmortems, and human feedback on every prediction.
  • Per-service baselines with seasonality, and a memory trend detector.
  • The LLM answer engine evaluated per prompt version on the same questions.
